# 第5章 実装技法

本章は、D3/D2 の GPU 実装で採用した技法と、検討して採用しなかった案を、開発者向けに説明します。ファイル構成とカーネルの一覧は 04 章、理論式は 02 章、検証結果は 06 章にあります。

出典の略記は 04 章と同じです（`D3:n` = `src/force/dftd3.cu` の n 行目、`D2:n` = `src/force/dftd2.cu`、`P3:n` = `dftd3para.cuh`）。性能の数値は、すべて RTX A6000（sm_86、84 SM）、CUDA 12.3、NEP89、`dftd3 pbe 12 6` での nsys 測定です [DES-0001、各 VER]。他の GPU や HIP では測定していません。「導出」「推論」とあるものは、記録やコードから本マニュアル作成者が導いたもので、実行して確認していません。

## 5.1 D3 の計算フロー

D3 の 1 ステップは、**配位数（CN）→ 力（ペア項）→ extra（CN 微分項）**の 3 段階です。小箱経路では、その前に近傍リストの構築が、大箱経路では、前にセルリストの構築が入ります（04 章 4.4 節の図）。

| 段階 | カーネル（小箱 / 大箱） | 入力 | 出力 |
|---|---|---|---|
| 1. CN | `find_dftd3_coordination_number_small_box` / `…_large_box` | 位置、`rc_cn` 内の近傍 | `cn`、`cn_weight`（5 個／原子）、（大箱のみ）CN リスト |
| 2. 力 | `add_dftd3_force_small_box` / `find_dftd3_force_large_box` | `cn`、`cn_weight`、`rc_pot` 内の近傍 | エネルギー、ペア項の力、ビリアル、`dc6_sum`、`dc8_sum` |
| 3. extra | `add_dftd3_force_extra_small_box` / `find_dftd3_force_extra_large_box` | `dc6_sum`、`dc8_sum`、`rc_cn` 内の近傍 | CN 微分による力とビリアル |

### 段階の間の依存

- 力カーネルは、ペアの両端の CN を必要とします（C6 が両原子の CN に依存するため）。したがって CN カーネルが全原子分を終えてから力カーネルを起動します。
- extra カーネルは、力カーネルが書く `dc6_sum`、`dc8_sum` を必要とします。したがって力カーネルの後です。

この依存のため、3 つのカーネルを 1 つに融合することはできません [VER-0015：extra は力カーネルの `dc6_sum`/`dc8_sum` を必要とし、力カーネルは両原子の CN を必要とする]。

### extra が表すもの

D3 のエネルギーは、ペアの距離 r だけでなく、両原子の配位数 CN_i、CN_j（C6 を通じて）にも依存します。したがって力は、

- **ペア項**：r への明示的な依存の微分（力カーネルが計算）、
- **CN 項**：CN が r に依存することによる微分（extra カーネルが計算）

の和になります（式の導出は 02 章）。この CN 項が「extra」です。

コード上は次のようになっています。

1. 力カーネルは、ペアごとに `dc6`（C6 の CN 微分）を求め、原子ごとに合計を作ります（`D3:614-615`）。

```cpp
// D3:614-615（add_dftd3_force_small_box、ペアループ内）
    dc6_sum += dc6 * dftd3_para.s6 * damp_6;
    dc8_sum += dc6 * c8_over_c6 * dftd3_para.s8 * damp_8;
```

2. extra カーネルは、`rc_cn` 内の各相手について CN 関数 `1/(1+exp(-16((Rcov_1+Rcov_2)/r − 1)))` の r 微分に対応する係数 `k12` を作り、`D = dc6_sum + dc8_sum` を掛けて力にします（`D3:726-732`）。原子 1 に作用する力は `k12·(D_1 + D_2)·r12` です。

```cpp
// D3:726-732（add_dftd3_force_extra_small_box）
    const float cn_exp_factor = exp(-16.0f * ((R_cov_1 + R_cov_2) / d12 - 1.0f));
    const float dc_sum_2 = g_dc6_sum[n2] + g_dc8_sum[n2];
    float k12 = cn_exp_factor * 16.0f * (R_cov_1 + R_cov_2); // not 8.0f
    k12 /= (cn_exp_factor + 1.0f) * (cn_exp_factor + 1.0f) * d12 * d12_2;
    const float f2 = k12 * (dc_sum_1 + dc_sum_2);
    const float f2_virial = k12 * dc_sum_2;
```

3. ビリアルへの配分は、相手の `D_j` だけを使います（`f2_virial`）。原子ごとのビリアルは非対称になりますが、全体の和は正しい、という設計です（`D3:672-674` のコメント、UPSTREAM-0002 G）。

**CN のカットオフは `rc_cn`、ペア項のカットオフは `rc_pot`** と別々です。そのため extra カーネルは、力カーネルとは別の近傍リスト（通常は `rc_cn` ≤ `rc_pot` なので、より短いもの）を使います。小箱では `NL_angular`、大箱では angular セルリストまたは CN リストです。

## 5.3 複数スレッド／原子と固定順序の木縮約

### 構成

`num_sub` 個（2 の冪）の連続スレッドが 1 原子 n1 を担当します（`D3:543-546`）。

```cpp
// D3:543-546（add_dftd3_force_small_box）
  const int tid = threadIdx.x;
  const int sub = tid % num_sub;
  const int n1 = blockIdx.x * (blockDim.x / num_sub) + tid / num_sub;
  const bool valid = n1 < N;
```

- 小箱：スレッド `sub` は近傍リストの `sub, sub+num_sub, …` 番目の要素を処理します（`D3:570`）。
- 大箱：スレッド `sub` は、近傍セルの `sub, sub+num_sub, …` 番目のセルを処理します（`D3:953`、`1080`）。
- 各スレッドは、エネルギー、力 3 成分、ビリアル 9 成分、`dc6_sum`、`dc8_sum` を float のレジスタに累積します。

### 縮約

部分和を共有メモリ `s_red[値の番号][スレッド番号]` に置き、オフセットを `num_sub/2` から 1 まで半分にしながら足し込みます（`D3:497-509`）。

```cpp
// D3:497-509
template <int num_sub, int num_values>
__device__ __forceinline__ void
reduce_sub_large_box(float (*s_red)[BLOCK_SIZE_LARGE_BOX], const int tid, const int sub)
{
  for (int offset = num_sub / 2; offset > 0; offset >>= 1) {
    __syncthreads();
    if (sub < offset) {
      for (int k = 0; k < num_values; ++k) {
        s_red[k][tid] += s_red[k][tid + offset];
      }
    }
  }
}
```

```text
num_sub = 8 の例（sub = 0..7 の部分和 p0..p7）
offset 4:  p0+=p4, p1+=p5, p2+=p6, p3+=p7
offset 2:  p0+=p2, p1+=p3
offset 1:  p0+=p1           → 結果は sub == 0 のスレッドにある
```

足す順序は `num_sub` だけで決まり、スレッドのスケジューリングに依存しません。結果を書くのは `sub == 0` のスレッドだけで、`g_fx[n1] += s_fx` のように**自分の原子の要素へ 1 回だけ**書きます（`D3:655-669`）。つまり、出力の各要素を書くスレッドは 1 つだけで、競合する書き込みがありません。

### 設計上の注意

- `__syncthreads()` を含むため、ブロック内の**全スレッド**がこの関数を呼ぶ必要があります。端数ブロックの無効スレッド（`n1 >= N`）も、原子 0 を読んで（`n1_safe`）ループを実質空にし、縮約には参加して、書き込みだけを省きます（`D3:546-548, 635-637`）。
- 小箱では `num_sub` が最大 128 で、ブロック 128 を割り切る必要があります（`static_assert`、`D3:539-542`）。大箱は最大 16 です。
- 共有メモリは `s_red[15][128]` の float で 7,680 B です。
- `num_sub = 1` のときはブロックを 64 にし、縮約をしません（`num_sub > 1` の分岐、`D3:617`）。このとき累積順序は master と同じです [VER-0004 §1]。
- 同じ構造が D2 にもあります（`SubReduce<NUM_SUB>`、`D2:265-343`。共有メモリ `s_red[13][128]` は double）。

### 決定性の性質と限界

| 性質 | 内容 | 出典 |
|---|---|---|
| D3 に `atomicAdd` がない | `dftd3.cu` に `atomicAdd` は残っていません。出力要素ごとに書き手は 1 スレッドです | `grep` の結果、DES-0001 Phase 7 |
| 小箱経路 | 近傍リストの順序が直列アルゴリズムと同一（候補番号の順）で、縮約順序が `num_sub` で固定なので、**同じバイナリ・同じ GPU・同じ入力で実行ごとにビット一致**します。`num_sub` = 1〜128 のすべてでテストされています | `test_dftd3_small_box_all_threads_per_atom_agree_and_are_reproducible`、VER-0013 |
| 大箱経路（D3 のカーネル） | CN・力・extra の各カーネル自体は決定的（固定順序の縮約）です | 上記 |
| **大箱経路（セルリスト）** | セルリスト構築 `find_cell_list` は、`find_cell_contents` で整数の `atomicAdd` を使い（`neighbor.cu:80`）、**セル内の原子順序がスケジューリングに依存**します。このため float の累積順序が実行ごとに変わり、**ビット再現性は保証されません**。実際、大箱ケース（水 5,184、Cu 4,000、クラスター 972）では、元のコードでも最適化後でも `thermo.out` が実行ごとに異なります。NEP 単体はビット再現的でした | VER-0014 Other checks、VER-0015、01 章 1.10 節 |
| テストでの扱い | 大箱のビット一致テストは、24 原子・1 ワープの系だけで行っています（1 ワープならセルリストの順序が毎回同じになるため）。大きな大箱系のビット一致は主張していません | `test_dftd3_large_box_neighbor_list_is_exact_and_reproducible` |
| D2 | 力・エネルギー・ビリアルに `atomicAdd` はなく、`atomicAdd` は整数のセルカウンターだけ（`D2:177, 220`）です。セル内の並びは `place_atoms` が元の番号の昇順に直すので、決定的です。水 2,187 原子・`rc` = 30 Å でビット一致をテストしています | 5.6 節、`test_dftd2_dense_water_is_bitwise_reproducible` |
| `num_sub` が異なる場合 | 足す順序が変わるため、float の丸めの範囲で結果が変わります。AC-1 の上限内に収まることをテストしています | VER-0013、`test_dftd2_all_threads_per_atom_agree_and_are_reproducible` |

**決定性の適用範囲（導出）**：`num_sub` は GPU の SM 数（`multiProcessorCount`）から決まる `target_threads` に依存します（04 章 4.5 節）。したがって、**異なる GPU 間では `num_sub` が変わり得て、丸めレベルの差が出る**と考えられます。この点は異なる GPU で確認していません。

### スレッドを増やしすぎない理由（小箱の走査）

小箱の走査表 [VER-0013]（力カーネル、ms）によれば、N が数千を超えると、`num_sub` を大きくするほど遅くなります。

| N | 既定 | 1 | 4 | 16 | 128 |
|---|---|---|---|---|---|
| 81 | 0.019 | 1.099 | 0.284 | 0.081 | 0.019 |
| 2,187 | 0.144 | 1.384 | 0.381 | 0.144 | 0.188 |
| 8,748 | 0.442 | 1.323 | 0.419 | 0.952 | 0.686 |

理由（コードのコメントと VER-0013 の記述）：カーネルは遅延律速（リスト要素ごとの依存するグローバルロードの連鎖）で、スレッド数を増やすと遅延を隠せますが、多すぎると 1 ワープのリスト読み出しが多くの行に分散して遅くなります（`D3:792-799`）。規則は「`N × num_sub` を SM 数 × 640 以下」にとどめます。

## 5.4 因数分解した C6 重み、float 累積、W < 1e-30 の fallback

### C6 補間の因数分解

D3 の C6 は、参照配位数の格子上の値 `c6_ref[a][b]` を、ガウス重み `L_ab` で補間した値です。重みは

```text
L_ab = exp(-4 (CN_1 − CNref_1[a])²  − 4 (CN_2 − CNref_2[b])²)
     = w_1[a] · w_2[b]            w[k] = exp(-4 (CN − CNref[k])²)
```

と因数分解できます（コードの説明は `D3:56-60`）。master は、ペアごとに `a, b` の二重ループで `exp` を計算していました（最大 25 回）。本フォークでは、次のようにします。

1. CN カーネルが、原子ごとに 5 個の重み `w[k]`（`max_cn = 5`、`num_cn` を超える参照点は 0）を `cn_weight[n·5 + k]` に保存します（`store_cn_weights`、`D3:61-73`）。メモリは 1 原子あたり 20 B（N = 41,472 で 0.83 MB）です [VER-0014]。
2. 力カーネルは、中心原子の重み `w`、`dw = w·(−8·diff)`、およびその和を `load_cn_weights` で 1 回だけ読みます（`D3:84-104`）。
3. ペアごとに `get_c6_factorized`（`D3:107-163`）が、相手原子の重みを 5 個読み、積と和だけで Z、dZ、W、dW を作ります。

```cpp
// D3:138-162（get_c6_factorized の要点）
  float Z = 0.0f;  float dZ = 0.0f;
  for (int a = 0; a < max_cn; ++a) {
    if (a < num_cn_1) {
      float t = 0.0f;
      for (int b = 0; b < max_cn; ++b) {
        if (b < num_cn_2) { t += c6_pair[a * stride_a + b * stride_b] * w2[b]; }
      }
      Z  += cw.w[a]  * t;
      dZ += cw.dw[a] * t;
    }
  }
  float W = cw.sum_w * sum_w2;
```

`W = (Σ w_1)(Σ w_2)` は、因数分解しない場合の `Σ L_ab` と、丸めを除いて等しくなります [VER-0014]。`c6 = Z/W`、`dc6 = dZ/W − c6·dW/W²` です（`D3:159-161`）。`c6_ref` の添字は、元素対 `(z_small, z_large)` について格納されており、`z1 < z2` かどうかで a と b の歩幅を入れ替えます（`D3:132-137`）。

- 両原子の `num_cn` が 1 のときは、`c6 = c6_ref の先頭要素`、`dc6 = 0` の近道があります（`D3:121-124`）。
- 参照データの添字 `z12 = z_small·max_elem − z_small(z_small−1)/2 + (z_large − z_small)`（`D3:579`）で、`c6_ref` は 94 × 95 / 2 = 4,465 対 × 25 = 111,625 個です（導出）。

効果と限界：D3 合計で、水 5,184 が 1.21 倍、クラスター 972 が 1.23 倍、水 41,472 が 1.10 倍、他は 1.02〜1.08 倍で、遅くなる例はありませんでした。水 41,472 の目標（6.0 ms 以下）は未達でした（6.931 → 6.316 ms）。C6 を定数に置き換えた上限（5.59 ms）に届かないのは、C6 の参照表の二重和がペアループに残り、レジスタが 72 から約 80 に増えるためです [VER-0014]。結果は丸めレベルで変わり、AC-1 / AC-2 の許容値内です。

### float 累積

ペアの和（エネルギー `s_pe`、力 `s_fx…`、ビリアル `s_sxx…`、`dc6_sum`、`dc8_sum`）は、スレッドのレジスタ内で **float** で累積します（`D3:555-569`）。最後に、`sub == 0` のスレッドが **double の per-atom 配列に 1 回だけ** `+=` します（`D3:655-667`）。CN も float（`cn_temp`、`D3:181`、`934`）です。

小箱の最適化の前は、float の項を double の `atomicAdd` で加えていました。float 累積への変更は丸めレベルの変更で、AC-1 の許容値内であることを確認しています（最大の変化は graphite の dE：3.94e-6 → 4.63e-6、許容値は 7.88e-6 [VER-0013]）。

D2 は、DR-004 の R3（2026-11-06、ADR-0005）の前は逆で、ペアの項は float、**累積は double** でした（`D2:383-385, 436-470`、以下の行番号はこの変更前のもの）。R3 以降は、ペアの項は float のまま、累積を **TwoSum で補償した float の和**にし、4 セルごとに double の累積へ足します（`CompensatedSum`、`PairSums`、`FLUSH_CELLS = 4`。サブスレッドの縮約は double のまま、atomic なし）。FP64 が FP32 の 1/64 の GPU で、カーネル時間が約 78 % 減りました（VER-0026 §4、R3 の Stage 2 の記録）。

### W < 1e-30 の fallback（upstream 由来の挙動）

```cpp
// D3:154-162
  float W = cw.sum_w * sum_w2;
  const float dW = cw.sum_dw * sum_w2;
  if (W < 1.0e-30f) {
    c6 = c6_pair[(num_cn_1 - 1) * stride_a + (num_cn_2 - 1) * stride_b];
  } else {
    W = 1.0f / W;
    c6 = Z * W;
    dc6 = dZ * W - c6 * dW * W;
  }
```

`W` が 1e-30 未満になると、最後の参照対の C6 を使い、`dc6 = 0`（CN 依存の力を落とす）とします。この規則は upstream の元のコードと同じで、因数分解の導入前からあります。float の `exp(−4 diff²)` は、CN がどの参照 CN からも約 4.2 以上離れるとアンダーフローするため、極端な CN で誤った C6 が選ばれます。参照実装（simple-dftd3）は倍精度で、より遠くまで正規化した重みを保ち、それを超えると最大 CN の参照を使います。H 原子のように「最後の参照」が最大 CN でない元素では、誤った参照を選びます [UPSTREAM-0001、VER-0017]。通常の NEP89 の MD 系（水、結晶、有機物）では AC-1 の許容値内で影響が出ません。因数分解で挙動は変わっていません [VER-0014、UPSTREAM-0001 冒頭]。

## 5.5 CN カーネルと extra カーネルのリスト共有

### 動機

大箱経路では、CN カーネルと extra カーネルは同じ angular セルリスト、同じ `rc_cn`、同じペア判定を使います。つまり extra カーネルの近傍走査は、CN カーネルの走査の 100% の繰り返しです。受理されるペア 1 つあたり約 4〜4.5 個の候補を訪れます [VER-0015、`D3:855-858` のコメント]。

### 仕組み

CN カーネルは、受理した相手の番号を、スロットごとのリストに保存します。スロットは `(原子 n1, sub)` の組で、`slot = n1·num_sub + sub` です（`D3:935-936`）。

```cpp
// D3:974-990（find_dftd3_coordination_number_large_box）
          if (d12_2 < rc * rc) {
            ...
            cn_temp += 1.0f / (exp(-16.0f * ((R_cov_1 + R_cov_2) / d12 - 1.0f)) + 1.0f);
            if (num_accepted < list_capacity) {
              g_list[num_accepted * num_slots + slot] = n2;
            }
            ++num_accepted;
          }
  ...
  if (valid && list_capacity > 0) {
    g_list_count[slot] = num_accepted;
  }
```

- リストの配置は `g_list[k·num_slots + slot]` で、同じ `k` のスロット間でメモリが連続（コアレッシング）します。
- `num_accepted` は容量を超えても数え続けるので、`g_list_count` は「実際に受理した個数」で、溢れを検出できます。

extra カーネルは、スロットの個数を読み、**全員が収まった場合だけ**リストを使い、そうでなければセル走査を元通り繰り返します（`D3:1278, 1317-1340`）。

```cpp
// D3:1278、1317-1321（find_dftd3_force_extra_large_box）
  const int num_listed = (valid && list_capacity > 0) ? g_list_count[slot] : -1;
  ...
  if (num_listed >= 0 && num_listed <= list_capacity) {
    for (int k = 0; k < num_listed; ++k) {
      add_pair(g_list[k * num_slots + slot]);
    }
  } else { /* セルを走査して add_pair(...) */ }
```

### 容量・溢れ・同一性

| 項目 | 内容 |
|---|---|
| 容量 | 4.3 節の規則。`int(min(1.5·expected_pairs/num_sub, 4096)) + 8`。256 MB を超えるなら 0（リスト不使用） |
| 溢れ | 容量不足のスロットは走査に戻る。「容量が小さすぎると時間が増えるだけで、精度は変わらない」（`D3:858-860` のコメント）。水 41,472、5,184、Cu 4,000、クラスター 972 の初回ステップで、既定容量では溢れるスロットが 0 でした（他の密度については主張していません）[VER-0015] |
| 同一のペア順序 | リストは CN カーネルの走査順に作られ、extra カーネルのセル走査も同じ順序（`c = sub, sub+num_sub, …` のセル、各セル内は `cell_contents` の順）です。同じステップで同じ angular セルリストを使うので、セルリストの原子順序が実行ごとに変わっても、**同一ステップ内では、リスト経由でも走査でも同じペアが同じ順序で処理されます**（`D3:1273-1275` のコメント）。したがって float 累積順序も同じです（容量 {既定, 0, 1, 4} がビット一致することをテスト、`test_dftd3_large_box_neighbor_list_is_exact_and_reproducible`） |
| 保存するもの | 相手の番号（int）だけ。float の `r12` も保存する変形は、メモリ転送が増えて遅く（0.85 倍）、却下 [VER-0015 `cachef`] |
| メモリ | `N × num_sub × capacity × 4 B` + `N × num_sub × 4 B`。水 41,472 で 31.6 MB + 1.3 MB（capacity 25）、水 5,184 で 4.0 MB、Cu 4,000 で 3.7 MB、クラスター 972 で 0.5 MB [VER-0015] |
| 確保 | 増える方向にだけ再確保し、25% の余裕を持たせる（上限 256 MB の範囲内）。NPT で体積が変わると容量が変わるためで、`resize()` が解放と確保を伴うからです（`D3:1606-1619`） |
| レジスタ | CN カーネル 50 → 55、extra カーネル 63 → 72（スピルなし）[VER-0015] |

効果：extra カーネル 0.760 → 0.200 ms（水 41,472、3.8 倍）、D3 合計は水 5,184 で 1.04 倍、Cu 4,000 で 1.07 倍、クラスター 972 で 1.28 倍でした。小箱経路のコードは変更していません [VER-0015]。

小箱経路には、同様のリスト共有はそもそも不要です。小箱は完全な近傍リスト `NL_angular` を持ち、extra カーネルがそれをそのまま使うからです。

## 5.6 D2：近傍リストなし、コスト基準のセル数、NUM_SUB スレッド、セル中心相対の float4 候補ループ

### 全体

D2 は、近傍リストを保存せず、分数座標上の**セルリスト**を直接走査します（`D2:27-37` のヘッダコメント）。力・ビリアルは per-atom のレジスタ（double）に累積し、力への `atomicAdd` はありません。同一のカーネルが、セルがカットオフより小さい場合も大きい場合も扱います（周期イメージを含めて近傍セルを訪れる）。全ペアを両方の原子から評価するので、エネルギーは `0.5·φ_sf` ずつ加えます（`D2:451`）。

### コスト基準のセル数（`choose_cell_counts`、`D2:500-555`）

方向ごとのセル数 `n[d]` の候補は、1 と `floor(kk · width_d / rc)`（`kk = 1..6`、`MAX_CELL_RANGE = 6`）で、各候補は `cbrt(max_cells)` 以下に制限します。すべての組合せ `(n_x, n_y, n_z)` について、次のコストを評価して最小のものを選びます（毎回ホストで実行）。

```text
k_d           = ceil( rc / (width_d / n_d) * (1 + 1e-12) )          （近傍セル範囲）
cells_visited = Π_d (2 k_d + 1)        （非周期方向は min(2 k_d + 1, n_d)）
cost          = N * cells_visited / num_cells  +  3.0 * cells_visited
                └ 訪れる候補原子数（一様密度）    └ セルを訪れるコスト（CELL_VISIT_COST）
```

`CELL_VISIT_COST = 3.0` は、水と Cu、`rc` = 12〜30 Å での、強制セル数での実測時間（40 点）に合わせた値です（フィットの rms 対数誤差 0.14）[VER-0008 §2]。検証は、フィットに使った系に、フィットに使わなかったカットオフ（14、16、18、25）と水 20,736 を加えたものです。

旧規則は固定の `n = floor(2·width/rc)` で、水 648 原子（箱 18.6 Å）では `rc` ≥ 18.6 Å でセル数が 2 から 1 に落ち、全原子が 125 イメージ（`k = 2`）を走査して 16 → 20 Å で時間が 4〜4.8 倍に跳ねました [DES-0002 Phase 6 Stage 1 (c)]。コスト基準にして跳びは解消し、水 648 原子で 1.62 倍（`rc` = 30 Å）、2.28 倍（20 Å）、どの系も 1.03 倍より遅くなりませんでした [VER-0008]。

### NUM_SUB スレッド（`get_num_sub`、`D2:562-570`）

`NUM_SUB`（最大 32、2 の冪）個の連続スレッドが 1 原子を共有し、各近傍セルで `NUM_SUB` 個おきの原子を処理します（`D2:427`）。縮約は 5.3 節と同じ固定順序の木で、`atomicAdd` を使いません。選択規則は 04 章 4.5 節です。効果：水 648、`rc` = 30 Å で、セル数の変更に上乗せして 9.4 倍（合計 15.2 倍）。D2 の追加時間は N = 648 で 54.3 → 2.92 ms、N = 41,472 で 211 → 117 ms でした [DES-0002 Stage 2、VER-0008]。

### セル中心相対の float4 候補ループ

候補原子の位置を、**自分のセルの中心からの相対座標**にして `float4` で保持します（`place_atoms`、`D2:246-259`）。ペアベクトルは、次のように作ります。

```cpp
// D2:422-434（dftd2_pair_kernel の候補ループ）
        const float ofx = static_cast<float>(by0 + ox * grid.C[0]);   // セル中心間の変位（double で作り、1 回だけ float に丸める）
        ...
          const float dx = (pj.x - pi.x) + ofx;
          const float dy = (pj.y - pi.y) + ofy;
          const float dz = (pj.z - pi.z) + ofz;
          const float r2 = dx * dx + dy * dy + dz * dz;
          if (r2 >= rc2) { continue; }
```

**誤差の評価**（`D2:30-36`、VER-0009 §1）：オフセット（最大で約 `k·w`、すなわち約 `rc`）を float に丸め、和をもう一度丸めるので、ペアベクトルの各成分の絶対誤差はおよそ `6e-8 × (r + w)`（r はペア距離、w はセル幅）です。これは箱の大きさにも、原点からの距離にも依存しません。近いペアでは、厳密な double ベクトルを 1 回だけ丸めた場合（約 `6e-8·r`）の最大 `(1 + w/r)` 倍になります（例：r = 3 Å、w = 12 Å で約 5 倍、2e-7 → 1e-6 Å）。

| 変形 | AC-1 許容値に対する最大誤差の割合 | 採否 | 出典 |
|---|---|---|---|
| 候補を double（旧） | 0.03〜0.14（float のペア演算由来） | － | VER-0009 §2 |
| 絶対座標の float（`fa`、試験のみ） | 0.29〜0.73、原点から +100 Å の系で **2.53（不合格）**。ペアベクトルが反対称でなく、合力が `Fmax` の 1e-5 に | 不採用 | VER-0009 §2 |
| セル中心相対の float（`fb`） | 最大 0.27（ゲート 1/3 以下）。合力は `Fmax` の 3e-16〜6e-15 程度 | **採用** | VER-0009 §2 |

採用の効果：ペアカーネル 1.49〜1.86 倍（水 648、5,184、Cu 4,000、`rc` = 12〜30 Å の 35 点）、遅くなる例なし、レジスタ 34（変更なし）[VER-0009 §3]。ペアベクトルは i ↔ j で厳密に反対称（同じ float 演算で符号が反転するだけ）なので、合力は丸めの範囲でゼロです（VER-0009 §1）。ペアの項（`r`、`exp`）は float、累積は double です。シフト項 `φ(rc)`、`φ'(rc)` は初期化時に double で求めて float に落とします（`D2:659-666`）。`rc` 自体も初期化時に一度 float に丸め、カットオフ判定、シフト項、セル探索で同じ値を使います（`D2:622-624`）。

### 決定的な並び

`list_atoms` はセルごとの原子リストを `atomicAdd` で作るため、順序はスケジューリング依存ですが、`place_atoms` は「同じセルで番号が小さい原子の数」を数えて順位にし（`D2:243-245`）、元の番号の昇順に並べ直します。これにより、並べ替え後の順序が決定的になります。`list_atoms` の出力は中間データにとどまります（`dftd2.cuh:68`）。

## 5.7 検討して採用しなかった案

### (a) float による前段フィルタ（DES-0001 Phase 7 項目 (vii)、VER-0016）

**案**：大箱の CN カーネルで、候補の座標差を float（セル中心相対）で作り、ガード帯付きで `r < rc` を判定する。通過した候補と帯の内側の候補だけ、倍精度の距離を再計算する。受理ペアの集合と受理ペアの倍精度演算は変えない。

**結果**：ゲート（CN カーネル 1.2 倍以上）を満たさず、**かえって遅くなりました**（水 41,472 で 0.93 倍、水 5,184 で 0.86〜0.92 倍）。`src/` の変更は残していません [VER-0016、DES-0001 項目 (vii) 結果]。

**理由（SIMT の性質）**：全候補の約 22% が受理されます。ワープは 32 スレッドが同時に進むので、あるワープ反復で少なくとも 1 スレッドが受理される確率は `1 − 0.78³² ≈ 99.965%`（導出）で、ほぼすべてのワープ反復が、全レーンについて倍精度の経路を（述語付きで）実行します。前段フィルタは、倍精度の仕事を省けず、float の仕事が上乗せされるだけです。倍精度演算を持たない float 版（`cn_xf32`）の CN カーネルは 0.711 → 0.375 ms でしたが、これは結果が変わる（非同一）変形です。得るには、受理候補のワープ内圧縮（compaction）か、float だけで判定する（結果が変わる）方法が必要でした。前者は最小限の試作を超え、後者は項目の「同一性」要件に反するため、追求しませんでした。

### (b) 半近傍リストと `atomicAdd`

- D3：DES-0001 Phase 5 の原因 C（半リスト、アトミックが必要）は「条件付き（Phases 2-4 の後に、なお正当化される場合のみ）」で、実装した証拠は見つかりませんでした（結果は未記載。本マニュアル作成者による確認）。`atomicAdd` の削除（Phase 7 (i)）の方向とも逆です。小箱では、倍精度アトミック（ペアあたり 15 回）が、スレッド数を増やしたとき N = 8,748 で 1.6 倍のコストになると見積もられていました [VER-0012]。
- D2：DES-0002 Phase 6 Stage 2 (iv)（`atomicAdd` を使う半リスト）は、超越関数の部分が 2% 未満で効果が小さく、決定性を失うため、追求しませんでした [DES-0002 Stage 1 結果、Stage 2 結果]。

### (c) 小箱のセルリスト・パラメータ（DES-0001 Phase 7 項目 (ii)）：保留

小箱の近傍リスト構築は O(N²) で、(i)（力・extra の複数スレッド化）の後は D3 合計の大きな割合を占めます（水 81 で 39%、648 で 77%、2,187 で 72%、8,748 で 94% [VER-0013]）。それでも、(ii)（小箱のセル／リストのパラメータをコスト基準で選ぶ）は、**人間の判断で保留**されました。記録された理由は「AC-4 に必要ない」です [DES-0001 Phase 7 Stage 2 結果]（AC-4 の小箱側の目標 N = 81、648 は (i) で達成済み）。保留であり、却下や不可能の判断ではありません。5.9 節の未解決事項です。

### 決定性のまとめ

| 経路 | 累積の順序 | `atomicAdd` | 実行ごとのビット一致 | 証拠 |
|---|---|---|---|---|
| D3 小箱 | 近傍リスト順 × 固定順序の木（`num_sub` で決まる） | なし | **一致**（同一バイナリ・同一 GPU・同一 `num_sub`） | テストで確認（`num_sub` = 1〜128）、小箱 water 648 の 100 ステップ NVE の `thermo.out` もビット一致 [VER-0014] |
| D3 大箱 | セルリスト順（`atomicAdd` に依存）× 固定順序の木 | カーネルになし。セルリスト構築（共有コード）に整数の `atomicAdd` | **保証されない** | 大箱の `thermo.out` が実行ごとに異なる [VER-0014]。最適化前も同じ |
| D2 | 元の番号の昇順（`place_atoms`）× 固定順序の木 | 整数カウンターのみ | **一致**（同一バイナリ・同一 GPU・同一 `NUM_SUB`） | `test_dftd2_dense_water_is_bitwise_reproducible`、`…_all_threads_per_atom_agree_and_are_reproducible` |

限界：

1. ビット一致は、同じバイナリ・同じ GPU・同じ `num_sub` のときの主張です。GPU の SM 数が変わると `num_sub` が変わり得るため（導出）、GPU 間の一致は主張できません。
2. `num_sub` が異なれば、丸めレベルで結果が変わります（AC-1 の上限内）。
3. 大箱の D3 は、セルリスト構築の整数 `atomicAdd` のために実行ごとにずれます。ただし、実測で確認されているのは `thermo.out` が実行ごとに異なることまでで、ずれの大きさの全体像は記録に無いです。VER-0004 の記録では、`num_sub = 1` の同じバイナリの 2 回の実行で力が 1.3×10⁻⁵ eV/Å 以内で食い違いました（NEP 側のセルコードを含む系全体の値で、D3 単独の寄与は分離されていません）。
4. 大箱の D3 のビット一致テストは、24 原子の系だけです。
5. 他の GPU（sm_86 以外）、他の CUDA バージョン、HIP での決定性は未確認です。

## 5.10 まとめ

| 技法 | 目的 | 副作用・限界 |
|---|---|---|
| ブロック／原子 + スキャンによる小箱の近傍リスト | O(N²) 走査の並列化。リストの順序は不変 | 計算量は O(N²) のまま、メモリは 320 kB／原子 |
| 複数スレッド／原子 + 固定順序の木縮約 | 小さな N で GPU を埋める。`atomicAdd` を排除し決定性を得る | 丸めレベルの変化。N が大きいとスレッドを増やすと遅くなる |
| C6 の因数分解（`cn_weight`） | ペアループから `exp` を除く | +20 B／原子、レジスタ増。アンダーフロー挙動は upstream と同じ |
| CN リスト共有 | extra の走査の繰り返しを省く | 最大 256 MB の追加メモリ。溢れたら走査に戻る |
| D2 のコスト基準のセル数 | カットオフ依存の跳びを除く | 一様密度の仮定 |
| D2 のセル中心相対 float4 | FP64 の負荷を下げる | 誤差 `6e-8 (r + w)`。AC-1 の 1/3 以下を確認 |
